# T446: нестабильный кэш llmkit на dev (вывод из кода, без доступа к стенду)

**Не проверено на стенде:** у меня нет доступа к воркеру Windmill dev; ниже — вывод из `src/llmkit/cache.py` и `core.py`. Подтвердить: на воркере `llm config path --json` и `ls -l` файла кэша.

## Что в ключе кэша
`make_key`: sha256 от JSON (sort_keys) из `provider/model`, `api_base`, `messages`, `schema` (model_json_schema), `temperature`, `max_tokens`. Теги, task_id, время, порядок providers в routing в ключ **не входят**; ключ считается на каждую модель цепочки отдельно. Температура — число из настроек, форматирования нет. Порядок vars влияет, только если он попал в текст `messages` (рендер шаблона): другой порядок → другой ключ.

## Причина
Кэш — **локальный SQLite-файл** (`platformdirs.user_cache_dir/cache.sqlite`, TTL 30 дней), не БД стенда. `st_llmkit@stand-pg` хранит только `llmkit_calls` (usage). В Windmill несколько воркеров/контейнеров, у каждого свой файл (или он пропадает при пересоздании контейнера):
- запуск на воркере A → miss, платный ответ, запись в файл A; на воркере B → свой miss и другой ответ (temperature 0.3) в файл B; на A снова → hit. Отсюда `from_cache`=1 вперемешку с платными и **разные** ответы даже при hit (файлы разных воркеров).
- Внутри одного файла гонка тоже есть: `get`→вызов→`INSERT OR REPLACE`; два параллельных запуска оба промахнутся, последний перезапишет первого — ответ под ключом меняется.
- TTL и lookup-багов не нашёл: протухшее отдаётся как miss, чтение по PK.

## Что делать
1. Сейчас (настройка): общий файл для всех воркеров — `[cache] path = "<путь на общем томе>"` в конфиге llmkit (env для пути нет, только `LLMKIT_CACHE` вкл/выкл). SQLite на сетевом томе ненадёжен.
2. Правильно (код): кэш в общей БД (`LLMKIT_DATABASE_URL`, таблица `llmkit_cache`, миграция 0003) + `INSERT … ON CONFLICT DO NOTHING` (первый ответ побеждает, ключ стабилен). Это minor-релиз 0.12.0, нужен эпик.
3. Малая правка без БД: `INSERT OR IGNORE` вместо `OR REPLACE` — закрывает только гонку внутри файла.
